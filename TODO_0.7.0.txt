Code Review — webMARS
Repositório: codigoavulso/webMARS · Versão 0.6.5 · Branch main · 23/10/2026

A análise incide sobre o código-fonte, a arquitetura, a segurança, o funcionamento do simulador, a gestão de projetos, a infraestrutura e os testes. Não consultei o conteúdo de nenhum README.md.

O webMARS é um projeto consideravelmente maior do que uma simples interface para executar Assembly: inclui um assembler MIPS, um motor de simulação, um compilador Mini-C, ferramentas de análise de execução, persistência local, sincronização cloud e um sistema de publicação de projetos.

1. Problemas encontrados
Alta prioridade Importação de projetos com risco de colisão e perda de dados
Ficheiro: 21-project-manager.js, linhas 644–664

Na função importFile(), a verificação de nomes duplicados compara nomes de projetos com caminhos completos, que incluem a extensão .p.

Por exemplo, com um projeto existente chamado teste.p, importar outro chamado teste pode produzir:

existing = new Set(["teste.p"]);
candidate = "teste";

existing.has(candidate); // false

A função não deteta a colisão e atribui ao novo projeto o mesmo rootPath, teste.p.

Isto entra em conflito com a lógica de normalização da biblioteca, que elimina entradas com o mesmo caminho de raiz, e com o índice rootKey único do IndexedDB.

Consequência: o projeto importado pode desaparecer da biblioteca normalizada, criar divergências entre as cópias armazenadas ou impedir a atualização do IndexedDB.

Correção: comparar sempre os caminhos de raiz normalizados, incluindo a extensão, e garantir um identificador de projeto não utilizado antes de gravar.

Alta prioridade Persistência sem transação única entre localStorage e IndexedDB
Ficheiros:

20-app-runtime.js, linhas 775–852

20-project-repository.js, linhas 154–174

O método saveProjectAndLibraryData() tenta manter a consistência entre os dados locais, mas as operações de espelhamento para IndexedDB são assíncronas e os respetivos erros são ignorados.

Há um cenário problemático concreto:

A nova biblioteca é escrita no localStorage.

É iniciado o espelhamento assíncrono para IndexedDB.

A gravação do projeto ativo falha, por exemplo devido à quota de armazenamento.

O código restaura os valores anteriores no localStorage.

O espelhamento iniciado anteriormente não é cancelado e pode persistir a biblioteca que acabou de ser rejeitada.

Além disso, o gestor de projetos prefere os registos do IndexedDB quando estes existem, introduzindo a possibilidade de apresentar informação divergente da utilizada pelo runtime.

Consequência: inconsistência entre projetos visíveis, projetos efetivamente ativos e dados recuperados posteriormente.

Correção: estabelecer uma única fonte de verdade e efetuar gravações consistentes. O ideal seria IndexedDB como armazenamento principal, com transações completas, migração controlada e um mecanismo explícito de recuperação.

Alta prioridade A reciclagem dos projetos não está ligada à eliminação normal
Ficheiros: 20-app-runtime.js, linhas 5405–5434 e 21-project-manager.js, linhas 583–615

O gestor apresenta uma localização intitulada Recycle bin. Existe até uma função moveToTrash() que prepara os dados para recuperação.

O problema é que essa função não é chamada pelo fluxo normal de eliminação.

Quando se elimina um projeto pela árvore, a operação chama diretamente removeProjectFromLibrary(). Esta remove o projeto da biblioteca, sem o colocar na reciclagem.

Consequência: um utilizador pode eliminar um projeto, procurar recuperá-lo na reciclagem e descobrir que não está lá.

Este é um dos problemas que corrigiria primeiro, sobretudo numa aplicação utilizada para escrever e guardar código.

Prioridade média A reciclagem pode mostrar projetos ativos quando IndexedDB não está disponível
Ficheiros: 20-project-repository.js, linhas 176–180 e 21-project-manager.js, linhas 91–101

No método listProjects(options), quando IndexedDB não está disponível, o código devolve sempre os projetos locais, ignorando options.trash.

Assim, listProjects({ trash: true }) pode devolver os projetos ativos, que depois são apresentados pelo gestor como elementos da reciclagem.

O fallback deve distinguir explicitamente entre a biblioteca de projetos e a biblioteca de eliminados.

Prioridade média Falha no carregamento de módulos deixa a aplicação bloqueada no ecrã inicial
Ficheiros: app.bundle.js, linhas 50–79 e index.html, carregamento inicial

Quando um módulo JavaScript falha ao carregar, o loader adiciona uma mensagem de erro ao #app e interrompe a sequência.

Contudo, o ecrã inicial só desaparece quando é recebido o evento webmars:tools-ready, que pode nunca ocorrer após essa falha.

O utilizador fica com o ecrã de carregamento sobreposto à mensagem de erro. O temporizador apenas altera o texto para indicar que o arranque está a demorar.

Correção: criar um evento terminal de falha, apresentar o módulo afetado e disponibilizar uma opção de recarregamento.

3. Outros problemas relevantes
Alta prioridade Eliminar um projeto local também pode eliminar a cópia cloud
Este é, potencialmente, o problema com maior impacto sobre os dados do utilizador.

Ficheiros: 20-app-runtime.js, linhas 3282–3319 e 20-app-runtime.js, linhas 1867–1902

A remoção de um projeto utiliza este comportamento por defeito:

if (options.deleteFromCloud !== false) {
  void deleteCloudProjectsByName(
    normalizeProjectRootPath(
      removedProject?.rootPath || rootPath,
      "project"
    )
  );
}

A função chamada procura projetos remotos com o mesmo nome normalizado e envia pedidos HTTP DELETE para cada correspondência.

A confirmação apresentada na árvore de projetos limita-se a perguntar se o utilizador pretende eliminar o projeto. Não esclarece que a operação também pode afetar a cloud.

Cenário: um utilizador autenticado quer remover apenas uma cópia local para libertar espaço. Ao confirmar, pode desencadear a eliminação da correspondente versão remota.

A eliminação remota é assíncrona e não bloqueia a eliminação local em caso de erro, podendo ainda produzir estados parcialmente sincronizados.

Recomendação: separar explicitamente Eliminar deste dispositivo de Eliminar também da cloud, com confirmação específica para a segunda operação. Uma eventual proteção contra o reaparecimento dos projetos durante a sincronização deve utilizar um mecanismo próprio, e não uma eliminação remota implícita.

Prioridade média Exportação de publicações arquivadas não tem o fallback utilizado pela abertura
Ficheiro: 21-project-manager.js, abertura e 21-project-manager.js, exportação

Ao abrir uma publicação própria arquivada, o código contempla recuperar a última revisão disponível se o pedido normal falhar.

Na exportação, esse fallback não existe: o código tenta apenas a rota normal /publications/{slug}.

Consequentemente, a publicação pode conseguir ser aberta, mas falhar ao ser descarregada, dependendo do comportamento da API relativamente a publicações arquivadas.

A solução é centralizar a obtenção de uma publicação numa única função reutilizada pelas operações de abrir, consultar e exportar.

Risco de segurança condicionado Servidor de desenvolvimento permite aceder a ficheiros internos do repositório
Ficheiro: scripts/serve.mjs, linhas 45–107

O servidor estático valida que o caminho pedido se encontra dentro do diretório do repositório. Essa é uma proteção útil contra path traversal convencional.

Contudo, não restringe os ficheiros servidos aos recursos públicos da aplicação. Um pedido dirigido a .git/config, por exemplo, pode ser servido se esse ficheiro existir no diretório de execução. Também não existe proteção explícita contra symlinks que apontem para fora da raiz.

Por defeito, o servidor escuta apenas em 127.0.0.1, o que reduz substancialmente a exposição.

O risco torna-se relevante se o servidor for disponibilizado na rede, por exemplo através de HOST=0.0.0.0.

Correção: servir exclusivamente um diretório de distribuição, bloquear ficheiros ocultos e verificar o caminho real (realpath) antes de abrir ficheiros.

Prioridade média As gravações individuais do IndexedDB não aguardam a conclusão da transação
Ficheiro: 20-project-repository.js, linhas 56–67

A função auxiliar request() resolve a promessa no evento onsuccess do pedido, não no evento oncomplete da transação.

Para leituras, isso é normalmente suficiente. Para escritas, o sucesso de um pedido não garante, por si só, que a transação inteira tenha sido confirmada.

A implementação já espera corretamente pelo transaction.oncomplete em algumas operações, como mirrorLibrary(), mas não mantém essa regra em saveProject() e saveSession().

Recomendo uniformizar o comportamento, aguardando a conclusão da transação para todas as escritas.

Prioridade média Importação de ficheiros sem limite antecipado de dimensão
Ficheiro: 21-project-manager.js, linhas 644–665

O importador executa await file.text() e JSON.parse(text) antes de verificar o tamanho ou a complexidade do projeto.

Em contrapartida, o carregamento de projetos públicos possui limites explícitos para o número de ficheiros, a dimensão individual e o tamanho total.

Um ficheiro de importação excessivamente grande pode provocar consumo significativo de memória ou bloquear a interface durante a análise e serialização.

Deveria existir uma validação antecipada de file.size, seguida de validação estrutural antes de persistir o projeto.

5. Desempenho
O carregador inicial referencia 23 ficheiros JavaScript, representando aproximadamente 2,28 MB de código não comprimido, e carrega os módulos sequencialmente.

Referência: app.bundle.js, carregamento dos módulos.

Isto não significa que sejam transferidos 2,28 MB pela rede: compressão HTTP e cache podem reduzir substancialmente o tráfego. Mas a quantidade de código inicial também afeta análise e execução JavaScript.

A opção mais útil seria carregar determinadas funcionalidades apenas quando necessárias, particularmente o compilador Mini-C e alguns módulos auxiliares.

Em contrapartida, há decisões positivas no ciclo de execução: o runtime executa instruções por lotes, utiliza limites de tempo por iteração e evita atualizar toda a interface a cada instrução. São mecanismos importantes para manter a aplicação responsiva.

6. Segurança
O resultado é relativamente positivo na parte do navegador, mas incompleto no que respeita à cloud.

O gestor de ficheiros aplica escape HTML a nomes, caminhos e atributos que introduz na interface. Os projetos públicos passam por validação de caminhos e limites de dimensão. O coletor de métricas aceita um conjunto limitado de campos e eventos, e a configuração impede o envio das métricas para uma origem arbitrária.

Estas são boas escolhas.

Também não encontrei, nos principais módulos inspecionados, utilização de eval() ou new Function() para executar código fornecido pelo utilizador.

Por outro lado, o servidor BackMars não faz parte do código analisado. Assim, não seria correto afirmar que a autenticação, as permissões de acesso, a proteção CSRF ou a eliminação de projetos na API estão seguras. Os testes de autenticação existentes utilizam respostas simuladas da API em vários cenários.

Existe ainda uma distinção importante em matéria de privacidade: embora o coletor de métricas evite recolher IP nos eventos, a configuração de logs Nginx inclui campos como endereço IP, User-Agent e Referer. É uma superfície de dados diferente e deve ter uma política de retenção adequada.

7. Qualidade dos testes
A existência de quase 500 testes no job principal é um ponto bastante favorável. Há testes para instruções MIPS, memória, syscalls, interrupções, execução reversível, compilação, pipeline, ferramentas e robustez perante entradas inválidas.

Particularmente positivos são os testes de fuzzing determinístico, os testes de invariantes de memória e os mecanismos de comparação diferencial com MARS.

Contudo, a revisão identificou uma lacuna evidente: os caminhos de criação, importação, eliminação, reciclagem, restauração e sincronização de projetos precisam de testes de integração conjuntos. Os testes individuais de módulos não são suficientes para detetar todas as inconsistências entre localStorage, IndexedDB, interface e cloud.

Seria também vantajoso integrar a comparação diferencial MARS 4.5 no CI regular, quando for viável disponibilizar legalmente o artefacto de referência.

9. Avaliação final
O meu diagnóstico é que o webMARS tem uma base técnica forte no motor de simulação e nos testes, mas a gestão do ciclo de vida dos projetos não apresenta o mesmo nível de robustez.

A maior preocupação não é a correção das instruções MIPS: nos percursos analisados, não identifiquei um defeito concreto no núcleo de execução que justifique classificá-lo como incorreto. A preocupação principal são as operações sobre dados persistentes, sobretudo quando envolvem simultaneamente o navegador e a cloud.

A aplicação está numa fase em que a próxima melhoria importante deveria ser menos orientada para acrescentar funcionalidades e mais orientada para consolidar as existentes.

Conclusão: manteria a arquitetura global, evitaria uma reescrita e concentraria os próximos esforços na integridade dos projetos, no isolamento das operações destrutivas e em testes de integração completos. Até isso estar corrigido, recomendaria exportações de segurança para projetos importantes.

Limites desta revisão: analisei a árvore do repositório e os principais módulos e fluxos, mas não executei localmente a aplicação nem percorri linha a linha todos os 2 039 ficheiros. Os resultados de testes apresentados provêm dos logs do GitHub Actions. As falhas descritas como confirmadas resultam da leitura dos caminhos de execução; os riscos condicionados foram identificados separadamente. Nenhum README.md foi aberto ou lido, e não alterei qualquer ficheiro do repositório.
